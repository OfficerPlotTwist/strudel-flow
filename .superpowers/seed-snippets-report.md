## Why storage.js
`seedLibrary` is a thin orchestration over `loadLibrary`/`saveLibrary` plus the pure `addEntry`/`findEntry` primitives from `library.js` — it belongs next to the functions it composes rather than in a third module. It still takes an injected `storage` object (never touches `localStorage` directly, never imports DOM), so it stays as unit-testable as the rest of `storage.js`. `seed-snippets.js` stays separate and pure (just data) so the content itself can be reviewed/edited without touching any logic.

## Merge semantics implemented
- A `SEEDED_KEY` list in storage records every seed name ever *processed* (added or skipped-because-already-present), independent of the main library's `KEY`.
- On each call: for every seed not yet in the seeded list — if no snippet of that name exists, add it via `addEntry`; regardless, the name is appended to the seeded list.
- A seed already in the seeded list is never touched again, even if currently absent (deleted) or present with edited content.
- Writes: `SEEDED_KEY` is written only if the seeded list actually grew; the library is saved only if an entry was actually added. No-op runs do zero `storage.setItem` calls.
- Whole function wrapped in try/catch; falls back to `loadLibrary(storage)`, then `emptyLibrary()`, so a storage failure can never throw during boot. No competing alert is raised (the existing `saveLibrary` failure path in `panel.js`'s `persist()` already owns that).

## Hand-traced scenarios
**(a) First load, fresh browser** (`KEY` and `SEEDED_KEY` both absent):
`loadLibrary` returns `emptyLibrary()`. Neither seed name is in the (empty) seeded set, and `findEntry` finds neither. Both `piano_arp` and `dnb_chill` are added via `addEntry`. Result: library has 2 snippets, `SEEDED_KEY` is written as `["piano_arp","dnb_chill"]`, and the library itself is written under `KEY`. Two `setItem` calls total.

**(b) Second load** (same browser, nothing else changed):
`SEEDED_KEY` already contains both names, so the loop's `if (seededSet.has(seed.name)) continue;` skips both immediately. `nextSeeded` stays identical to the loaded list, `seededChanged` stays false, `libChanged` stays false. Zero `setItem` calls; no duplicates.

**(c) User deletes `dnb_chill`, then reloads**:
Panel calls `removeEntry` + `saveLibrary` on delete, so `KEY` now holds only `piano_arp`. `SEEDED_KEY` still contains `["piano_arp","dnb_chill"]` from the first load. On reload, both seed names are already in the seeded set, so the loop skips both — `dnb_chill` is not re-added despite being absent from the library. It stays deleted.
